# 项目交付与变更治理 v1

## 1. 文档层级

```text
项目章程：为什么做、边界和项目级成功标准
→ 分域 Spec：用户行为、业务规则和验收标准
→ 总体/分域设计：系统怎样满足要求
→ 主实施计划：工作包、顺序、依赖和退出门禁
→ 状态台账：当前事实、证据、负责人和阻塞
→ 执行日志：每次变更、验证、决策和遗留
```

下游不能覆盖上游。发现设计或实现需要改变上游约束时，先提交文档变更。

## 2. 开工门禁

一个工作包可以开工，必须满足：

- 在 `master-implementation-plan-v1.md` 中有 ID。
- 对应需求和验收标准已存在。
- 影响的架构、数据、权限、API 和 UI 已识别。
- 依赖工作包达到要求状态。
- 测试数据、验证命令和回滚策略明确。
- `delivery-status-v1.md` 标记为开发中并写当前范围。

不满足时只允许做调研或补设计，不进入产品实现。

## 3. 变更分类

| 级别        | 例子                           | 必需动作                        |
| ----------- | ------------------------------ | ------------------------------- |
| L1 实现细节 | 内部重构、文案、非契约样式     | 更新计划状态和日志              |
| L2 功能行为 | 新 API、新状态、验收变化       | 更新分域 Spec、设计、计划、测试 |
| L3 架构决策 | 数据真相源、运行时、权限、存储 | 新 ADR + 总体设计 + 主计划评审  |
| L4 产品范围 | 新用户旅程、SaaS、多租户       | 项目章程变更并重新排期          |

## 4. 迭代节奏

建议两周一个迭代：

- 迭代开始：从当前里程碑选择满足开工门禁的工作包。
- 迭代中：状态台账只记录事实，不把未验证代码标完成。
- 合并前：执行工作包门禁。
- 迭代结束：演示用户旅程，更新状态、日志、风险和下一迭代候选。
- 里程碑结束：执行完整退出门禁并产出验收记录。

## 5. 评审清单

### 需求评审

- 用户是谁、要完成什么动作、可观察结果是什么？
- 正常、无权限、空数据、失败和恢复如何表现？
- 是否改变历史证据、数据出域或人工确认边界？

### 设计评审

- 真相源和所有权是否唯一？
- 跨数据库/文件/队列的一致性怎样处理？
- 幂等键、并发锁、迁移和回滚是什么？
- 审计、监控、资源限制和敏感数据如何处理？

### 代码评审

- 是否关联工作包和 Spec？
- 是否只修改当前范围？
- 是否覆盖拒绝、失败和重试？
- 是否引入未批准依赖、外部调用或 Schema 破坏？
- 状态台账和日志是否有验证证据？

## 6. 质量门禁

基础门禁：

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

完整用户流程追加：

```bash
pnpm test:e2e
```

数据库、队列、文件或模型相关工作包还要运行对应集成/故障/安全测试。只有命令退出 0 且验收结果记录到台账，才算证据。

## 7. 风险管理

状态台账维护风险项：概率、影响、触发信号、缓解动作、负责人和复查时间。

优先跟踪：

- Markdown 文本检索规模上限。
- PDF/Office 定位准确率。
- 多模态工具的部署体积和 GPU 依赖。
- 文件系统与数据库跨存储一致性。
- Skill 沙箱在 macOS/Linux/容器环境差异。
- 云模型数据出域和成本失控。
- AI 题目/评分质量与人工复核成本。

## 8. 发布规则

- 里程碑内可以发布开发预览，但不得称为该里程碑完成。
- 发布版本必须关联验收记录、迁移说明和已知限制。
- 数据库或 Wiki Schema 变更必须提供升级前检查和恢复路径。
- 生产部署、外部发布和创建 PR 仍需用户明确授权。
