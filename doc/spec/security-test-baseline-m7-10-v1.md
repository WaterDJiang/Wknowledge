# M7-10 安全测试基线 Spec v1

## 1. 关联计划

- 工作包：`M7-10 安全测试`，依据 [主实施计划](../plan/master-implementation-plan-v1.md) 的越权、SSRF、压缩炸弹、提示注入与 Sandbox 验收要求。
- 当前切片：仓库级、离线、只读的标准安全扫描与可追溯分级；不直接把扫描结论当作生产渗透测试或整改完成。

## 2. 目标

- 建立认证授权/组织隔离、上传与 Blob/Wiki 路径、Skill/模型/Worker 执行边界五类攻击面的源代码安全基线。
- 每个报告问题均包含攻击者、入口、数据流、敏感操作、有效反证、影响、严重级别和可执行修复建议。
- 将确认的问题进入后续独立修复 Spec；未确认风险和未覆盖运行面保持明确的待验证状态。

## 3. 范围与规则

- 审查 `apps/`、`packages/`、`runtimes/`、`deploy/`、`skills/` 与必要根配置；排除 `node_modules`、构建产物、测试结果、`data/`、文档、Git 历史和任何 `.env*` 内容。
- 只允许本地静态搜索和源代码阅读；不得访问网络、生产环境、用户数据或密钥，不执行攻击性请求。
- 重点验证未登录/低权限用户跨组织或跨空间访问、CSRF/IDOR、路径穿越、上传与解析资源耗尽、命令执行、动态 Skill 权限/出网、Provider SSRF/凭据泄露、提示注入提权与日志泄露。
- 发现按 `critical`、`high`、`medium`、`low` 分级。没有现实攻击路径或只有特权自我操作的问题不作为漏洞，但须在扫描覆盖中说明反证或假设。
- 扫描工件放入受控临时扫描目录；项目文档只记录不含敏感正文的结论、工作包状态与后续修复排期。

## 4. 验收

- 安全扫描的清单、发现和覆盖工件均可生成，且报告标明已审查面、明确排除项、未解问题和完成度。
- 每个可报告发现经主执行者再次按当前源代码验证；不能以关键词命中、依赖猜测或历史代码作为结论。
- 若有 `critical`/`high`，不得将 M7-10 标记为已验证；对应修复必须有独立 Spec、回归测试和全仓质量门禁。
- 若无阻断问题，仍须保留动态 Sandbox、真实 Provider、隔离 staging、压缩炸弹和部署网络策略的运行时验证缺口。

## 5. 非范围

- 对生产系统的渗透测试、端口扫描、漏洞利用、密钥轮换、依赖升级、Docker 镜像供应链签名和外部合规认证。
- 未经独立 Spec 的源码修复或数据库/部署状态变更。
